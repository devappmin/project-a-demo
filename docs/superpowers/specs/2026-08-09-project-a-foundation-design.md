# Project A 기반 구조 설계

- 작성일: 2026-08-09
- 대상 프로젝트: `project-a-demo`
- 참고 전용 프로젝트: `project-a` (deprecated, 수정 금지)
- 엔진: Godot 4.7
- 우선 플랫폼: Windows PC, 키보드
- 상태: 사용자 승인 완료

## 1. 목적

Project A는 대화와 선택 분기가 중심인 2D 픽셀 탑다운 어드벤처 게임이다. 이 설계의 목적은 다음 기능이 서로 강하게 결합되지 않도록 새 프로젝트의 기반을 정하는 것이다.

- 플레이어 이동, 달리기, 충돌, 방향 애니메이션
- NPC와 오브젝트 상호작용
- 화자 이름, 초상화, 표정이 포함된 하단 대화 UI
- 선택지, 조건 분기, 상태 변화, 다중 엔딩
- 정신 오염도, 호감도, 스토리 플래그, 퀘스트, 인벤토리, 수집품
- 맵 전환과 퍼즐별 상태 유지
- 여러 수동 저장 슬롯과 자동 저장
- 비개발자가 프로젝트 폴더에 접근하지 않아도 되는 공동 대화 제작

첫 구현의 목표는 모든 시스템을 얕게 흉내 내는 것이 아니라, 샘플 방 하나에서 입력부터 저장 복원까지 전체 흐름을 검증하는 수직 슬라이스다.

## 2. 설계 배경

### 2.1 기획에서 확인한 요구

기획에는 교환일기 조각 수집, 기억 회복, 정신 오염도와 기억상실, 선택에 따른 관계 변화, 여러 엔딩, 조사 오브젝트, 퀘스트와 퍼즐이 포함된다. 따라서 대화는 단순 문자열 재생이 아니라 게임 상태를 읽고 바꾸는 내러티브 실행기여야 한다.

주요 근거:

- [프로젝트 A 기획](https://app.notion.com/p/2c9c036ff8fe8001888bfdfc2c96010f)
- [기승전결 및 엔딩 구도](https://app.notion.com/p/2c9c036ff8fe803d99d3eaaf9bc21c1e)

### 2.2 구형 프로젝트에서 참고할 것

구형 `project-a`에서 다음 개념은 유지할 가치가 있다.

- `CharacterBody2D` 기반 탑다운 이동
- 플레이어가 바라보는 방향의 상호작용 영역
- 대화 중 이동과 상호작용을 막아야 한다는 규칙
- 타임라인 기반 대화와 선택지의 사용 경험

다음 구조는 새 프로젝트로 가져오지 않는다.

- 플레이어 이동 코드가 Dialogic의 현재 타임라인을 직접 검사하는 결합
- 입력을 매 프레임 전역 EventBus 신호로 중계하는 구조
- 탐지 목록의 첫 번째 오브젝트를 무조건 선택하는 방식
- 대화, 입력 잠금, 저장 상태를 외부 플러그인 내부 상태에 의존하는 방식

### 2.3 Dialogic을 제외하는 이유

Notion을 작성 원본으로 사용하면 Dialogic 편집기는 공동 제작 흐름에 참여하지 않는다. 이 상태에서 Notion 데이터, 변환된 Dialogic 타임라인, Dialogic 런타임까지 세 계층을 운영하면 디버깅과 버전 관리가 복잡해진다. Dialogic 2는 현재 Alpha 단계이며 공식 릴리스도 저장 상태와 서브시스템의 호환성이 깨질 수 있음을 안내한다.

- [Dialogic 공식 릴리스](https://github.com/dialogic-godot/dialogic/releases)
- [Dialogic 공식 저장소](https://github.com/dialogic-godot/dialogic)

따라서 새 프로젝트는 필요한 기능만 가진 경량 대화 런타임을 직접 소유한다.

## 3. 확정된 제품 결정

### 3.1 공동 제작

- Notion이 대화와 선택 흐름의 공동 작성 원본이다.
- 디자이너는 Godot 프로젝트나 Git 저장소에 접근하지 않는다.
- 장면은 Notion 데이터베이스로 관리한다.
- 장면 페이지 안에서는 표가 아니라 대본처럼 위에서 아래로 읽히는 연결 보기를 기본으로 사용한다.
- 게임 조건과 상태 효과는 기본적으로 접혀 있어 대본 읽기를 방해하지 않는다.
- 개발자가 명시적으로 동기화할 때만 Notion을 읽는다.
- 게임 실행과 배포 빌드는 Notion에 접속하지 않는다.

### 3.2 플랫폼과 입력

- 첫 출시 대상은 Windows PC다.
- 키보드 입력을 먼저 완성한다.
- 입력 액션과 플레이어 제어를 분리해 게임패드를 나중에 추가할 수 있게 한다.
- 첫 범위에서 게임패드 지원 자체는 완료 조건이 아니다.

### 3.3 대화 표시

- 화면 하단에 고정된 대화창을 사용한다.
- 현재 화자의 초상화 한 장을 대화창 왼쪽에 표시한다.
- 화자 이름과 현재 표정을 표시한다.
- 대사 진행, 선택지 이동, 확정 입력은 대화 모드 전용 입력으로 처리한다.
- 일반 대화와 오브젝트 조사 문구가 같은 런타임과 UI를 공유한다.

### 3.4 저장

- 여러 수동 저장 슬롯을 제공한다.
- 자동 저장 슬롯 하나를 별도로 둔다.
- 맵 전환 완료 후와 중요한 선택 적용 직후 자동 저장한다.
- 자동 저장이 대화 도중 발생하면 다음에 실행할 안정적인 대화 노드 위치를 함께 저장한다.

## 4. 전체 아키텍처

시스템은 세 영역으로 분리한다.

```text
Notion 공동 작성 원본
  → Godot 에디터 전용 동기화·검증·컴파일
    → 프로젝트 내부의 버전 고정 데이터
      → Godot 런타임
```

### 4.1 Notion 공동 작성 원본

- 대화 장면 데이터베이스
- 장면별 대본형 페이지
- 구조화된 대화 블록 데이터베이스
- 캐릭터와 허용 표정 카탈로그
- 초안, 검토, 확정 상태와 댓글

### 4.2 에디터 전용 동기화

`tools/notion_sync`는 다음 순서를 수행한다.

1. 지정된 Notion 데이터베이스와 페이지를 읽는다.
2. 장면, 흐름, 대화 블록, 선택지, 조건, 효과를 내부 모델로 변환한다.
3. 참조와 값의 유효성을 검증한다.
4. 런타임용 JSON과 manifest를 임시 경로에 만든다.
5. 전체 검증이 성공한 경우에만 기존 정상 스냅샷을 교체한다.

Notion 인증 정보는 로컬 환경 또는 Git에서 제외된 로컬 설정에만 둔다. 저장소와 배포 빌드에는 인증 정보를 포함하지 않는다.

### 4.3 프로젝트 내부 스냅샷

- `data/generated/dialogues/*.json`: 실행 가능한 대화 그래프
- `data/generated/dialogues/manifest.json`: 원본 페이지, 동기화 시각, 데이터 버전, 해시
- `data/characters/*.tres`: 표시 이름과 표정 ID를 실제 로컬 텍스처에 연결하는 리소스

생성 결과를 저장소에 포함해 Notion 연결 없이도 다른 개발 환경과 빌드 시스템이 같은 콘텐츠를 재현할 수 있게 한다.

### 4.4 런타임

런타임은 생성된 스냅샷만 읽는다. 주요 서비스는 다음과 같다.

- `InteractionRouter`: 플레이어 씬 안에서 조사, 대화, 문, 아이템, 퍼즐 행동 실행
- `DialogueService`: `AppRoot/ServiceLayer`에서 대사 그래프 진행과 선택 처리
- `NarrativeState`: `GameSession`이 소유하는 직렬화 가능한 플래그, 수치, 퀘스트, 인벤토리 데이터
- `DialogueView`: 하단 대화 UI 표시와 UI 입력 전달
- `GameSession`: 현재 게임 모드와 입력 권한
- `SceneDirector`: 맵 전환과 스폰 지점 처리
- `SaveService`: 저장 슬롯, 자동 저장, 복원, 저장 버전 관리

### 5.1 Autoload 제한

Autoload는 다음 세 개만 기본으로 둔다.

- `GameSession`: 모드와 현재 플레이 세션 상태를 관리하고 `NarrativeState`를 소유
- `SceneDirector`: 맵 수명 주기와 전환
- `SaveService`: 슬롯과 직렬화

새 전역 서비스는 기존 세 서비스로 책임을 표현할 수 없는 경우에만 추가한다. 모든 신호를 한곳에 모으는 전역 EventBus는 사용하지 않는다. 가까운 객체 사이의 직접 참조와 명시적 Godot 신호를 우선한다.

## 6. 주요 컴포넌트

### 6.1 플레이어

`PlayerController`는 다음만 담당한다.

- 현재 이동 벡터를 속도로 변환
- `CharacterBody2D.move_and_slide()` 호출
- 걷기와 달리기 속도 선택
- 마지막 유효 방향 유지
- 방향과 이동 상태에 맞는 애니메이션 재생

`PlayerController`는 대화 서비스나 UI를 참조하지 않는다. 현재 모드에서 이동 입력을 받을 수 있는지는 별도의 입력 어댑터가 `GameSession`에 질의한다.

### 6.2 상호작용 탐지

`InteractionDetector`는 플레이어가 바라보는 방향의 후보를 수집하고 다음 순서로 하나를 고른다.

1. 상호작용 가능 여부
2. 명시된 우선순위
3. 바라보는 방향과의 각도
4. 플레이어와의 거리

선정된 대상에는 조사 안내를 표시한다. 대상이 겹쳐도 배열 삽입 순서에 결과를 의존하지 않는다.

### 6.3 상호작용 행동

모든 상호작용 대상은 현재 문맥에서 실행 가능한 행동을 제공한다. 첫 범위의 행동 종류는 다음과 같다.

- `Talk`: NPC 또는 오브젝트 대화 시작
- `Inspect`: 조사 문구와 간단한 연출
- `Pickup`: 아이템이나 기억 조각 획득
- `Door`: 조건 검사 후 맵 전환 요청
- `Puzzle`: 퍼즐별 컴포넌트에 제어 위임

`InteractionRouter`가 행동을 실행한다. 대상 씬은 대화 UI, 저장 서비스, 씬 트리를 직접 조작하지 않는다.

### 6.4 게임 모드

`GameSession`은 다음 모드를 가진다.

- `EXPLORATION`: 이동, 달리기, 상호작용
- `DIALOGUE`: 대사 진행과 선택지
- `CUTSCENE`: 연출 스크립트
- `MENU`: 메뉴 조작
- `TRANSITION`: 입력 잠금
- `PAUSED`: 일시 정지 입력

각 입력 소비자는 현재 모드에 허용된 액션만 받는다. 대화가 시작되면 `DIALOGUE`, 끝나면 이전의 정상 모드로 복귀한다. 개별 컴포넌트가 다른 시스템의 내부 상태를 검사해 입력을 막지 않는다.

## 7. Notion 대화 작성 모델

### 7.1 데이터베이스

세 데이터베이스를 사용한다.

#### Dialogue Scenes

- 제목
- 안정적인 `scene_key`
- 장소
- 상태: 초안, 검토, 확정
- 시작 흐름
- 담당자
- 대화 블록 관계

#### Dialogue Blocks

- 소속 장면
- 소속 흐름
- 순서
- 종류
- 화자
- 표정
- 본문
- 선택 대상 흐름
- 표시 조건
- 상태 효과
- 연출 명령
- 개발 메모

장면 페이지 안에는 현재 장면으로 필터링된 연결 보기를 둔다. 기본 보기에는 화자, 표정, 본문, 선택 흐름만 표시한다. 조건, 효과, 명령은 접힌 개발 보기에서 관리한다. 대화 블록의 Notion 페이지 ID를 내부의 안정적인 블록 ID로 사용하고, 사람이 줄 ID를 직접 관리하지 않게 한다.

#### Characters

- 안정적인 `character_key`
- 표시 이름
- 기본 표정
- 허용 표정 ID 목록
- 기획용 참고 이미지

실제 게임 텍스처 경로는 로컬 `CharacterDefinition.tres`가 소유한다. Notion은 표정 ID만 선택한다.

### 7.2 역할 분담

디자이너가 주로 편집하는 항목:

- 대사
- 화자
- 표정
- 선택지 문구
- 흐름 이름
- 연출 의도 메모

개발자가 주로 편집하는 항목:

- 안정적인 장면 키
- 조건식
- 상태 효과
- 게임 명령
- 잘못된 참조와 검증 오류

함께 관리하는 항목:

- 댓글
- 초안, 검토, 확정 상태
- 플레이 테스트 피드백

### 7.3 런타임 노드

컴파일된 대화 그래프는 다음 노드만 사용한다.

- `line`: 화자, 표정, 본문, 다음 노드
- `choice`: 표시 조건이 있는 선택 항목과 대상 노드
- `effect`: NarrativeState 변경
- `command`: 화면, 소리, 캐릭터 연출 요청
- `jump`: 다른 흐름 또는 장면으로 이동
- `end`: 대화 종료

조건과 효과는 임의 GDScript를 실행하지 않는다. 지원되는 연산자를 가진 구조화 데이터만 허용한다.

조건 예시:

- 플래그가 참 또는 거짓인지
- 수치가 기준 이상, 이하, 같은지
- 아이템이나 수집품을 보유했는지
- 퀘스트 상태가 특정 단계인지

효과 예시:

- 플래그 설정
- 수치 증가 또는 감소
- 아이템 추가 또는 제거
- 퀘스트 단계 변경
- 수집품 획득

## 8. 대화 실행 흐름

1. `InteractionDetector`가 현재 대상을 고른다.
2. 상호작용 입력이 `InteractionRouter`에 전달된다.
3. `Talk` 또는 `Inspect` 행동이 `DialogueService`에 장면 키를 전달한다.
4. `DialogueService`가 대화 데이터를 로드하고 `GameSession`을 `DIALOGUE` 모드로 바꾼다.
5. `line` 노드는 `DialogueView`에 이름, 표정, 본문을 보낸다.
6. `choice` 노드는 `NarrativeState`로 조건을 평가하고 표시 가능한 항목만 UI에 보낸다.
7. 선택 결과에 따라 `effect`를 적용하고 다음 노드로 이동한다.
8. `end`에서 UI를 닫고 이전 게임 모드로 돌아간다.

대화가 예외로 중단돼도 마지막 단계의 모드 복원은 반드시 실행한다.

## 9. 월드와 맵 씬

### 9.1 지속 AppRoot

Autoload와 `AppRoot`는 게임 시작부터 종료까지 유지한다. Autoload는 Godot의 `/root` 바로 아래에 있고 `AppRoot`의 자식으로 중복 배치하지 않는다.

```text
/root
├─ GameSession (Autoload, NarrativeState 소유)
├─ SceneDirector (Autoload)
├─ SaveService (Autoload)
└─ AppRoot
   ├─ ServiceLayer
   │  └─ DialogueService
   ├─ WorldHost
   │  └─ CurrentMap
   └─ UILayer
      ├─ DialogueView
      ├─ HUD
      └─ Menus
```

`SceneDirector`는 `WorldHost` 안의 현재 맵만 교체한다. 대화 UI와 세션 상태는 맵 전환 중에도 유지된다.

### 9.2 맵 씬 규격

각 맵은 다음 노드 그룹을 가진다.

- Ground
- Walls
- Props
- Actors
- Interactables
- EntryPoints
- Events

문은 목적지 `map_id`와 `spawn_id`만 알고 전환을 요청한다. 실제 씬 해제, 로드, 플레이어 배치는 `SceneDirector`가 담당한다.

영속적인 월드 오브젝트는 `map_id/object_id` 조합의 안정적인 키를 가진다. 열린 문, 획득한 아이템, 완료한 퍼즐 상태는 이 키로 저장한다.

## 10. 픽셀 렌더링

현재 데모 에셋은 16×16 타일과 48×48 캐릭터 프레임을 사용한다. 첫 렌더링 정책은 다음과 같다.

- 640×360의 16:9 논리 캔버스
- Nearest 텍스처 필터
- 정수 창 배율 우선
- Camera2D 줌 시작값 2×, 실제 플레이 테스트 후 고정
- 카메라와 스프라이트의 화면 좌표를 픽셀 경계에 정렬
- 월드 배율과 UI 배율 분리
- Y-sort 기준을 캐릭터 발 위치로 통일
- 창 크기는 변경할 수 있지만 내부 16:9 비율 유지

UI 글자는 논리 캔버스에서 직접 렌더링해 카메라 줌의 영향을 받지 않는다.

## 11. 저장 데이터

저장 파일은 Node 또는 Resource를 직접 직렬화하지 않고 버전이 있는 순수 데이터만 기록한다.

```text
SaveData v1
├─ meta
│  ├─ schema_version
│  ├─ saved_at
│  ├─ play_time_seconds
│  └─ slot_id
├─ player
│  ├─ map_id
│  ├─ spawn_id 또는 position
│  └─ facing
├─ narrative
│  ├─ flags
│  └─ stats
├─ progress
│  ├─ inventory
│  ├─ quests
│  └─ collectibles
├─ world
│  └─ map_id/object_id별 상태
└─ dialogue
   ├─ scene_key
   └─ next_node_id
```

### 11.1 안전한 저장

1. 새 데이터를 임시 파일에 기록한다.
2. 다시 읽어 스키마와 필수 값을 검증한다.
3. 기존 정상 저장을 백업으로 이동한다.
4. 임시 파일을 정식 슬롯 파일로 교체한다.

저장 버전이 다르면 명시적인 마이그레이션을 적용한다. 지원할 수 없는 버전은 기존 파일을 보존한 채 안전하게 거부한다.

### 11.2 맵 전환

맵 전환 순서는 다음과 같다.

1. `TRANSITION` 모드로 바꾸고 입력을 잠근다.
2. 전환 UI를 재생한다.
3. 기존 맵을 해제하고 새 맵을 로드한다.
4. 지정된 스폰에 플레이어를 배치한다.
5. 자동 저장한다.
6. `EXPLORATION` 모드로 복귀한다.

## 12. 오류 처리

### 12.1 Notion 동기화

다음 문제는 오류로 처리하고 새 스냅샷을 적용하지 않는다.

- 중복 장면 키
- 시작 흐름 누락
- 존재하지 않는 화자 또는 표정
- 끊어진 선택 대상이나 점프
- 지원되지 않는 조건, 효과, 명령
- 끝나지 않는 순환 중 명시적인 중단 지점이 없는 경우

오류는 장면, 흐름, 블록, 속성 위치와 수정 방법을 함께 표시한다. `초안` 장면은 비치명 경고와 함께 동기화할 수 있지만 `확정` 장면은 경고도 실패로 처리한다.

### 12.2 런타임

- 잘못된 대화 노드: 대화를 닫고 입력 모드를 복원한다.
- 배포 빌드의 대화 오류: 자연스러운 대체 문구를 표시하고 게임을 계속한다.
- 개발 빌드의 대화 오류: 장면 키와 노드 ID를 오류 화면과 로그에 표시한다.
- 잘못된 맵 또는 스폰: 이전 맵을 유지하고 입력 잠금을 해제한다.
- 손상된 저장: 정식 파일을 덮어쓰지 않고 백업 복원을 제안한다.

## 13. 테스트 전략

첫 기반에서는 외부 테스트 플러그인 없이 Godot headless로 실행되는 프로젝트 내부 테스트 러너를 사용한다. 테스트 규모가 커져 리포트와 픽스처 관리가 병목이 되는 시점에만 별도 프레임워크를 도입한다.

### 13.1 단위 테스트

- 조건 평가
- 상태 효과 적용
- 선택지 필터링
- 대화 노드 이동
- 게임 모드별 입력 허용
- 상호작용 대상 정렬
- SaveData 직렬화와 역직렬화
- 저장 버전 마이그레이션
- Notion 변환 데이터 검증

### 13.2 통합 테스트

- 대화 중 플레이어 이동과 상호작용 차단
- 선택 결과의 NarrativeState 반영
- 맵 전환 후 지정 스폰 배치
- 수동 저장과 자동 저장의 전체 왕복
- 동기화 실패 시 기존 스냅샷 유지

### 13.3 수동 플레이 테스트

- 대화창의 이름, 표정, 글자 출력 속도, 진행 입력
- 선택지 키보드 탐색과 확정
- 픽셀 흔들림과 Y-sort
- 상호작용 안내의 명확성
- 맵 전환 연출과 저장 완료 피드백

## 14. 첫 수직 슬라이스 완료 기준

다음 항목이 모두 충족돼야 기반 구현이 완료된 것으로 본다.

1. Notion 샘플 장면을 한 번의 동기화로 가져올 수 있다.
2. 플레이어 이동, 달리기, 충돌, 방향 애니메이션이 동작한다.
3. 바라보는 방향의 최적 오브젝트만 조사할 수 있다.
4. 대화 중 이동과 상호작용 입력이 차단된다.
5. 화자 이름과 여러 표정의 초상화가 표시된다.
6. 선택 결과가 플래그와 수치에 반영되고 재대화에도 유지된다.
7. 문을 통해 다른 맵과 지정 스폰으로 이동한다.
8. 수동 슬롯과 자동 저장을 불러오면 월드, 플레이어, 대화 상태가 동일하게 복원된다.
9. Notion 연결 없이 마지막 정상 스냅샷으로 게임을 실행하고 빌드할 수 있다.

## 15. 첫 수직 슬라이스에서 제외하는 범위

- 게임패드 완전 지원
- 다국어 현지화 파이프라인

- 범용 비주얼 대화 그래프 편집기

- 전체 본편 콘텐츠 입력
- 배포 플랫폼 연동과 업적
