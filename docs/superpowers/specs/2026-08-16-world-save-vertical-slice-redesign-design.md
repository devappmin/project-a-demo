# 월드·저장·수직 슬라이스 재설계

- 작성일: 2026-08-16
- 대상 프로젝트: `project-a-demo`
- 참고 전용 프로젝트: `project-a` (deprecated, 수정 금지)
- 엔진: Godot 4.7
- 상태: 사용자 승인 완료
- 대체 대상: `docs/superpowers/plans/2026-08-09-04-world-save-vertical-slice.md`의 구현 전 설계

## 1. 목적

이 설계는 지금까지 완성된 이동, 상호작용, document-first 대화 런타임 위에 실제 게임의 첫 번째 저장 가능한 수직 슬라이스를 만든다.

완료된 플레이 흐름은 다음과 같다.

1. 타이틀에서 새 게임을 시작한다.
2. 방을 이동하고 거울을 조사한다.
3. 이름, 초상화, 표정이 있는 대화를 진행한다.
4. 중요한 선택을 하고 다음 안정적인 대사 또는 선택지에 도착한다.
5. 자동 저장이 생성된다.
6. 문을 통해 두 번째 맵으로 이동한다.
7. 수동 슬롯에 저장한다.
8. 상태를 바꾼 뒤 저장을 불러온다.
9. 맵, 플레이어, 내러티브, 월드 오브젝트, 진행 중 대화가 정확히 복원된다.

저장 기능만 따로 붙이는 것이 아니라 맵 수명 주기, 안정적인 월드 상태, 메뉴, 오류 복구를 하나의 흐름으로 검증하는 것이 목표다.

## 2. 현재 기반과 호환 원칙

현재 프로젝트는 다음 기반을 이미 갖고 있다.

- `GameSession`과 `NarrativeState`
- 이동, 달리기, 충돌, 방향 애니메이션
- 상호작용 탐지와 `InteractionRouter`
- document-first 대화 문서와 수동 import
- `bundle_key + trigger_key`로 조건에 맞는 이벤트를 고르는 `DialogueEventResolver`
- 화자, 표정, 선택지, 효과를 처리하는 `DialogueService`
- 현재 방의 발 위치 기반 Y-sort와 별도 `PlayerVisual`

이번 설계는 이 기반을 교체하지 않는다. 특히 다음 규칙을 지킨다.

- 런타임은 Notion이나 네트워크를 사용하지 않는다.
- 대화의 외부 식별자는 `bundle_key + trigger_key`를 유지한다.
- 저장 파일에 Godot `Node`, `Resource`, 씬 인스턴스를 직렬화하지 않는다.
- `project-a`는 참고 전용이며 읽거나 수정하지 않는다.
- 기존 역사 문서와 구형 Plan 4는 보존하고, 이 문서를 기준으로 새 구현 계획을 작성한다.

## 3. 확정된 제품 결정

### 3.1 타이틀 메뉴

타이틀 메뉴에는 다음 세 항목만 둔다.

- 새 게임
- 불러오기
- 종료

별도의 `이어하기` 버튼은 만들지 않는다. 사용자는 `불러오기` 안에서 자동 저장과 수동 저장을 함께 확인한다.

`새 게임`은 메모리의 현재 세션을 초기화하고 시작 맵의 기본 스폰에서 시작한다. 기존 자동 저장이 있으면 `새 게임을 시작하면 자동 저장이 교체됩니다` 확인을 먼저 표시한다. 확인 후 첫 맵 배치가 성공하면 자동 저장을 새 게임 상태로 교체하되, 수동 슬롯 1–5는 그대로 유지한다.

### 3.2 불러오기 화면

불러오기 화면은 한 화면에 항상 여섯 행을 표시한다.

1. 자동 저장
2. 슬롯 1
3. 슬롯 2
4. 슬롯 3
5. 슬롯 4
6. 슬롯 5

각 행에는 다음 정보만 표시한다.

- 장소 이름
- 누적 플레이 시간
- 저장 시각

스크린샷은 표시하지 않는다. 빈 슬롯은 빈 상태가 분명하게 보이며 선택할 수 없다. 여섯 행은 640×360 논리 화면에서 스크롤 없이 모두 보여야 한다.

### 3.3 인게임 메뉴

탐색 중 `Esc`를 누르면 다음 메뉴를 연다.

- 계속
- 저장
- 불러오기
- 타이틀로

`저장`과 `불러오기`는 타이틀의 슬롯 행 컴포넌트를 재사용한다.

- 자동 저장 행은 `저장` 화면에서 읽기 전용이다.
- 수동 슬롯 1–5만 저장 대상으로 선택할 수 있다.
- 데이터가 있는 수동 슬롯에 저장할 때는 덮어쓰기 확인을 표시한다.
- `타이틀로`는 저장되지 않은 진행을 잃을 수 있으므로 확인을 표시한다.
- 메뉴를 닫으면 메뉴 진입 전의 탐색 상태로 돌아간다.

수동 저장은 `EXPLORATION` 또는 탐색에서 진입한 `MENU`에서만 가능하다. `DIALOGUE`, `CUTSCENE`, `TRANSITION` 중에는 메뉴를 열거나 수동 저장을 요청할 수 없다. 단순히 모드 값만 `MENU`로 바꿔 제한을 우회할 수 없도록 메뉴가 시작된 안전 모드를 함께 확인한다.

### 3.4 저장 피드백

화면을 막지 않는 짧은 알림으로 다음 상태를 알려준다.

- 저장했습니다
- 자동 저장했습니다
- 백업 저장을 복구했습니다
- 저장할 수 없습니다
- 불러올 수 없습니다

알림은 상세 오류를 사용자에게 그대로 노출하지 않는다. 개발 빌드 로그에는 슬롯 ID, 실패 단계, Godot 오류 코드를 남긴다.

## 4. 책임 분리

전역 서비스는 정확히 세 개만 사용한다.

### 4.1 `GameSession`

`GameSession`은 플레이 세션의 직렬화 가능한 상태를 소유한다.

- 현재 `GameMode`
- `NarrativeState`
- `WorldState`
- 누적 플레이 시간
- 새 게임 초기화
- 모드별 입력 권한

파일 시스템, 맵 씬 교체, 메뉴 노드에는 접근하지 않는다.

### 4.2 `SceneDirector`

`SceneDirector`는 `WorldHost`와 현재 맵의 수명 주기를 단독으로 소유한다.

- 맵 레지스트리 조회
- 후보 맵 생성과 사전 검증
- 입력 잠금과 화면 전환
- 현재 맵 교체
- 영속 플레이어 배치
- 맵 교체 후 동적 연결 재설정
- 성공한 맵 전환의 안정 지점 알림

저장 파일을 읽거나 쓰지 않는다.

### 4.3 `SaveService`

`SaveService`는 저장과 복원 흐름을 조율한다.

- 순수 저장 스냅샷 생성
- 슬롯 메타데이터 조회
- 원자적 저장소 호출
- 백업 자동 복구
- `SceneDirector`를 통한 복원용 맵 준비
- `GameSession`, 플레이어, 월드, 대화 상태 복원
- 자동 저장 요청 병합
- UI용 완료·실패·복구 신호

`SaveRepository`와 `SaveData`는 전역 서비스가 아닌 일반 클래스다.

## 5. AppRoot와 화면 구조

`AppRoot`는 게임 실행 동안 유지되고, 맵만 교체된다.

```text
/root
├─ GameSession       (Autoload)
├─ SceneDirector     (Autoload)
├─ SaveService       (Autoload)
└─ AppRoot
   ├─ ServiceLayer
   │  ├─ DialogueService
   │  ├─ DialogueActionAdapter
   │  └─ DoorActionAdapter
   ├─ WorldHost
   │  └─ CurrentMap 또는 비어 있음
   └─ UILayer
      ├─ ScreenFade
      ├─ InteractionPrompt
      ├─ DialogueView
      ├─ TitleMenu
      ├─ PauseMenu
      ├─ SlotMenu
      └─ ToastLayer
```

게임은 타이틀 UI가 열린 상태와 비어 있는 `WorldHost`로 시작한다. `새 게임` 또는 성공한 `불러오기`만 월드 맵을 활성화한다.

플레이어는 맵에 미리 박힌 인스턴스가 아니라 `SceneDirector`가 한 번 생성해 유지하는 영속 인스턴스다. 현재 `foundation_room.tscn` 안의 플레이어는 이 구조로 옮긴다. 물리 본체는 현재 맵의 액터 root에 붙이고, `PlayerVisual`은 같은 맵의 visual root에 붙인다. 맵을 바꿀 때 어느 한쪽도 기존 맵과 함께 해제되지 않아야 한다.

`AppRoot`는 현재 플레이어 경로를 하드코딩하지 않는다. `SceneDirector`가 맵을 확정할 때 현재 플레이어, `InteractionDetector`, `InteractionRouter`를 공개하고, `AppRoot`가 다음 연결을 다시 묶는다.

- `InteractionDetector` → `InteractionPrompt`
- `InteractionRouter.action_requested` → 대화 어댑터
- `InteractionRouter.action_requested` → 문 어댑터

이전 맵의 연결은 해제한 뒤 새 연결을 맺어 중복 실행을 막는다.

## 6. 맵 규격과 안전한 전환

### 6.1 맵 레지스트리

각 맵은 안정적인 `map_id`, 씬 경로, 기본 스폰을 가진 `MapDefinition`으로 등록한다. 첫 수직 슬라이스에는 다음 두 맵이 있다.

- `foundation_room`
- `foundation_hall`

각 `MapScene`은 다음 계약을 제공한다.

- 자신의 `map_id`
- 안정적인 `spawn_id` 조회
- 플레이어 물리 본체를 붙일 actor root
- 플레이어 시각 노드를 붙일 공통 Y-sort/visual root
- 맵 안의 영속 오브젝트 ID 등록과 중복 검사

### 6.2 전환 트랜잭션

일반 문 전환은 다음 순서를 따른다.

1. 목적지 `map_id`와 `spawn_id`의 형식을 검사한다.
2. 등록된 씬을 메모리에 후보로 생성한다.
3. 후보가 `MapScene`인지, `map_id`가 일치하는지, 스폰이 존재하는지 검사한다.
4. 현재 안전 모드를 기억하고 `TRANSITION`으로 바꾼다.
5. 화면을 페이드 아웃한다.
6. 현재 맵에서 플레이어 물리 본체와 `PlayerVisual`을 안전하게 분리하되, 기존 맵은 아직 해제하지 않는다.
7. 후보 맵을 `WorldHost`에 확정하고 플레이어를 지정 스폰에 배치한다.
8. `PlayerVisual`을 새 맵의 visual root에 다시 붙인다.
9. 상호작용 안내와 어댑터 연결을 새 플레이어 기준으로 다시 묶는다.
10. 해당 맵의 `WorldState`를 오브젝트에 적용한다.
11. 맵 전환 안정 지점을 발행하고 자동 저장을 요청한다.
12. 페이드 인한 뒤 `EXPLORATION`으로 돌아간다.

후보 검증이 끝나기 전에는 현재 맵을 해제하지 않는다. 검증 실패 시 후보만 제거하고 현재 맵, 플레이어, `PlayerVisual`, 내러티브 상태, 모드를 그대로 유지한다.

전환 중 예외가 발생해도 이전 맵을 다시 `WorldHost`에 붙이고 원래 연결, 플레이어, 시각 노드를 복구한다. 후보 맵의 월드 상태 적용과 동적 연결까지 모두 성공한 뒤에만 기존 맵을 해제한다. 현재 맵을 잃은 뒤 조용히 타이틀로 보내는 동작은 허용하지 않는다.

### 6.3 문 상호작용

문은 다음 데이터만 가진다.

```text
action: door
map_id: foundation_hall
spawn_id: from_room
object_id: to_hall
```

문 씬은 직접 씬 트리를 교체하지 않는다. `DoorActionAdapter`가 페이로드를 검증한 뒤 `SceneDirector`에 전환을 요청한다. 두 맵에는 왕복 문과 서로 대응하는 스폰을 둔다.

## 7. 영속 월드 상태

`WorldState`는 `map_id/object_id` 조합으로 오브젝트 상태를 보관한다.

```json
{
  "foundation_room": {
    "mirror": {
      "inspected": true
    }
  }
}
```

규칙은 다음과 같다.

- 같은 맵 안의 `object_id`는 중복될 수 없다.
- 상태 입력과 반환은 깊은 복사본이다.
- 지원하지 않는 값, Node, Resource, Callable은 거부한다.
- 맵을 나가기 전에 현재 오브젝트 상태를 캡처한다.
- 맵을 확정한 뒤 저장된 상태를 해당 오브젝트에 적용한다.
- 실패한 상호작용이나 실패한 맵 전환은 `WorldState`를 변경하지 않는다.

거울은 첫 표본으로 `inspected` 상태를 가진다. 대화의 조건과 효과는 계속 `NarrativeState`를 사용하고, 월드 표시나 일회성 오브젝트 상태는 `WorldState`를 사용한다. 두 상태가 같은 사실을 중복 소유하지 않도록 각 오브젝트가 하나의 소유 원칙을 정한다.

## 8. 저장 슬롯과 파일 규격

### 8.1 슬롯 ID

허용된 슬롯은 다음 여섯 개로 고정한다.

- `auto`
- `slot_1`
- `slot_2`
- `slot_3`
- `slot_4`
- `slot_5`

임의의 경로, 구분자, 다른 슬롯 ID는 저장소에 도달하기 전에 거부한다.

### 8.2 저장 데이터 v1

저장 파일은 다음 순수 JSON 구조를 사용한다.

```json
{
  "schema_version": 1,
  "checksum": "sha256...",
  "meta": {
    "slot_id": "slot_1",
    "saved_at": "ISO-8601",
    "play_time_seconds": 1234,
    "location_name": "기초 홀"
  },
  "player": {
    "map_id": "foundation_hall",
    "spawn_id": "from_room",
    "position": {"x": 120.0, "y": 88.0},
    "facing": "down"
  },
  "narrative": {},
  "world": {},
  "dialogue": {
    "active": true,
    "bundle_key": "foundation.inspect",
    "trigger_key": "mirror.inspect",
    "node_id": "stable-node-id",
    "boundary": "line"
  }
}
```

세부 규칙은 다음과 같다.

- `narrative`는 `NarrativeState.snapshot()`의 전체 순수 데이터다.
- 인벤토리, 퀘스트, 수집품은 별도 중복 섹션을 만들지 않고 현재 `NarrativeState` 계약 안에서 보존한다.
- `world`는 `WorldState.snapshot()`이다.
- `spawn_id`는 맵 복원 준비에 사용하고, 유효한 `position`이 있으면 최종 위치를 정확히 복원한다.
- `facing`은 `up/down/left/right` 중 하나다.
- `dialogue.active`가 `false`면 나머지 대화 필드는 비어 있어야 한다.
- 체크포인트는 현재 컴파일된 그래프에서 실제 `line` 또는 `choice` 경계인지 검증한다.
- 저장 내용이 현재 콘텐츠와 호환되지 않으면 현재 플레이를 바꾸지 않고 불러오기를 거부한다.

체크섬은 `checksum` 필드를 제외한 정규화된 데이터에 대해 계산한다. 스키마 버전이 다르면 명시적인 마이그레이션을 거치며, 지원하지 않는 버전은 원본 파일을 보존한 채 거부한다.

정규화는 Dictionary 키를 재귀적으로 정렬하고 Array 순서를 유지한다. 같은 스냅샷은 실행마다 같은 체크섬 입력을 만들어야 한다.

### 8.3 파일 배치

각 슬롯은 다음 세 경로만 사용한다.

```text
user://saves/<slot>.json
user://saves/<slot>.json.tmp
user://saves/<slot>.json.bak
```

슬롯 메타데이터도 본문 파일에서 읽는다. 별도 인덱스 파일을 두어 본문과 목록이 어긋나는 상태를 만들지 않는다.

## 9. 원자적 저장과 백업 복구

### 9.1 저장 순서

1. 메모리 스냅샷의 타입과 스키마를 검증한다.
2. 기존 현재 파일과 백업을 각각 읽어 어느 쪽이 마지막 정상본인지 확인한다.
3. 체크섬을 계산한다.
4. `.tmp`에 새 JSON을 기록한다.
5. `.tmp`를 다시 읽고 파싱, 스키마, 체크섬을 검증한다.
6. 현재 `.json`이 정상이면 기존 `.bak`을 정리하고 현재 파일을 `.bak`으로 이름 변경한다.
7. 현재 `.json`이 손상되고 `.bak`만 정상이면 정상 백업을 그대로 보존한 채 손상된 현재 파일만 교체 대상으로 삼는다.
8. `.tmp`를 현재 `.json`으로 이름 변경한다.
9. 새 현재 파일을 다시 검증한다.

중간 단계가 실패하면 기존 현재 파일 또는 백업을 이용해 마지막 정상 슬롯을 보존한다. 파일 시스템 단계별 실패를 테스트에서 주입할 수 있어야 한다.

### 9.2 읽기와 자동 복구

불러올 때 현재 `.json`을 먼저 검증한다.

- 현재 파일이 정상이면 그대로 사용한다.
- 현재 파일이 없거나 손상됐고 `.bak`이 정상이면 백업을 `.tmp`로 복사해 재검증한 뒤 현재 파일로 게시한다. 복구 중에도 원래 `.bak`은 유지한다.
- 복구 성공 후 `백업 저장을 복구했습니다` 알림을 표시한다.
- 현재와 백업이 모두 잘못됐으면 슬롯을 손상 상태로 표시하고 현재 플레이를 유지한다.

자동 복구는 조용히 데이터를 버리는 동작이 아니다. 원본 손상 파일은 진단 가능한 형태로 보존하거나, 복구 로그에 정확한 경로와 이유를 남긴다.

## 10. 자동 저장과 대화 체크포인트

### 10.1 자동 저장 시점

자동 저장은 두 경우에만 요청한다.

- 성공한 맵 전환과 플레이어 배치가 끝난 뒤
- 중요한 선택의 효과가 성공하고 다음 안정적인 경계에 도착한 뒤

같은 프레임이나 같은 전환 안에서 여러 요청이 발생하면 하나로 합친다. 저장 쓰기가 진행 중일 때 새 요청이 오면 최신 안정 지점 한 건만 대기시켜 직렬로 처리한다.

### 10.2 중요한 선택의 안정 지점

선택지를 누른 즉시 저장하지 않는다. 다음 순서를 모두 통과해야 한다.

1. 선택 항목의 효과를 트랜잭션으로 적용한다.
2. 다음 노드와 자동 `effect`, `command`, `jump` 구간을 정상 통과한다.
3. 다음 `line` 또는 `choice`가 UI에 게시된다.
4. 현재 `bundle_key`, `trigger_key`, 경계 `node_id`, 경계 종류를 캡처한다.
5. 자동 저장을 요청한다.

선택 뒤 대화가 정상 종료되면 내러티브 상태를 저장하되 `dialogue.active = false`로 기록한다. 효과나 다음 구간이 실패하면 기존 대화 트랜잭션을 복구하고 자동 저장하지 않는다.

`중요한 선택` 여부는 컴파일된 선택 항목의 명시적 메타데이터로 표현한다. 모든 사소한 선택을 자동 저장하지 않는다.

문서 작성자는 선택지 앞의 인용 메타데이터에 다음처럼 한글로 표시한다.

```text
> 자동 저장: 중요 선택
```

문서 import는 이를 선택 노드의 `autosave = true`로 정규화한다. 값이 없으면 기본값은 `false`다. 지원하지 않는 값은 경고로 추측하지 않고 import 오류로 처리한다. 이 메타데이터와 실제 저장 동작은 내러티브 상태 참조 문서에도 함께 기록한다.

### 10.3 대화 복원

대화 체크포인트를 불러올 때 조건 이벤트를 다시 선택하지 않는다. 저장된 `bundle_key`의 그래프와 정확한 안정 경계 `node_id`를 검증한 뒤 그 경계에서 재개한다. `trigger_key`는 원래 상호작용 문맥과 진단을 보존한다.

따라서 중요한 선택으로 바뀐 플래그 때문에 같은 트리거의 다른 이벤트가 선택되더라도, 불러온 직후에는 저장 당시의 다음 대사 또는 선택지부터 이어진다. 대화가 끝난 뒤 다시 상호작용하면 그때 현재 상태로 이벤트를 새로 고른다.

## 11. 불러오기 트랜잭션

불러오기는 현재 게임을 먼저 파괴하지 않는다.

1. 슬롯 파일과 필요 시 백업을 읽는다.
2. 체크섬, 스키마, 모든 필드 타입을 검증한다.
3. 맵, 스폰, 위치, 방향, 내러티브, 월드, 대화 체크포인트를 `RestorePlan`으로 해석한다.
4. 대상 맵 후보와 스폰을 현재 맵 밖에서 사전 검증한다.
5. 대화 체크포인트가 현재 그래프의 안정 경계인지 사전 검증한다.
6. 현재 메모리 세션과 기존 맵 인스턴스를 롤백용으로 보존한다.
7. `TRANSITION`으로 잠그고 페이드 아웃한다.
8. 후보 맵을 확정하고 플레이어를 배치한다.
9. `WorldState`, `NarrativeState`, 플레이 시간, 위치, 방향을 복원한다.
10. 동적 상호작용 연결과 `PlayerVisual`을 새 맵에 다시 붙인다.
11. 체크포인트가 있으면 `DialogueService`를 정확한 경계에서 재개한다.
12. 모든 복원이 성공한 뒤 기존 맵을 해제한다.
13. 페이드 인하고 최종 모드를 `DIALOGUE` 또는 `EXPLORATION`으로 설정한다.

사전 검증 실패는 현재 맵과 상태를 전혀 바꾸지 않는다. 확정 단계에서 예상하지 못한 실패가 발생하면 보존한 현재 세션과 맵을 복구한다. 타이틀에서 실패했다면 타이틀과 빈 `WorldHost`를 유지한다.

불러오기 성공 자체는 즉시 자동 저장을 만들지 않는다. 맵 복원과 일반 문 전환을 구분해 로드 직후 슬롯을 덮어쓰는 일을 막는다.

## 12. 모드와 입력

모드별 허용 입력은 다음과 같다.

| 모드 | 월드 이동·상호작용 | 대화 입력 | 메뉴 입력 | 수동 저장 |
|---|---:|---:|---:|---:|
| `EXPLORATION` | 허용 | 차단 | `Esc` 허용 | 허용 |
| `DIALOGUE` | 차단 | 허용 | 차단 | 차단 |
| `CUTSCENE` | 차단 | 차단 | 차단 | 차단 |
| `MENU` | 차단 | 차단 | 허용 | 탐색에서 진입한 경우만 허용 |
| `TRANSITION` | 차단 | 차단 | 차단 | 차단 |
| `PAUSED` | 차단 | 차단 | 제한적 | 차단 |

저장, 로드, 전환 요청이 중복 실행되지 않도록 각 서비스는 진행 중 상태를 공개하고 재진입을 거부한다. UI 버튼도 같은 상태를 반영해 비활성화한다.

## 13. UI 구성과 키보드 흐름

슬롯 행은 타이틀 불러오기, 인게임 저장, 인게임 불러오기에서 같은 씬을 사용한다.

```text
┌──────────────────────────────────────────────┐
│ 불러오기                                     │
│ 자동 저장  기초 홀   00:20:34   2026-08-16 │
│ 슬롯 1    젤리뽀 집  00:18:02   2026-08-16 │
│ 슬롯 2    비어 있음                          │
│ 슬롯 3    비어 있음                          │
│ 슬롯 4    비어 있음                          │
│ 슬롯 5    비어 있음                          │
│                                      뒤로    │
└──────────────────────────────────────────────┘
```

- 위/아래로 행을 이동하고 확정 키로 실행한다.
- 빈 슬롯과 저장 화면의 자동 저장 행은 포커스 대상에서 제외하거나 확정할 수 없게 한다.
- 현재 포커스는 픽셀 화면에서도 분명한 테두리와 색 차이로 표시한다.
- 저장 시각은 로컬 시간으로 표시하되 파일에는 ISO-8601 값을 보관한다.
- 플레이 시간은 `HH:MM:SS`로 표시한다.
- 긴 장소명은 한 행 안에서 잘리고, 행 높이나 전체 배치를 밀어내지 않는다.

## 14. 오류 처리

다음 오류는 모두 현재 플레이와 정상 저장을 보존하는 방향으로 실패한다.

- 등록되지 않은 맵
- 존재하지 않는 스폰
- 잘못된 저장 슬롯 ID
- 손상된 JSON
- 체크섬 불일치
- 지원하지 않는 스키마 버전
- Node 또는 Resource가 섞인 상태 데이터
- 유한하지 않은 플레이어 좌표
- 존재하지 않는 대화 번들 또는 노드
- `line`/`choice`가 아닌 대화 체크포인트
- 임시 쓰기, 재읽기, 백업 이동, 게시 이동 실패
- 저장 또는 로드 중 재진입

오류 알림은 사용자가 다음 행동을 할 수 있게 짧고 명확해야 한다. 상세 진단은 로그와 테스트용 구조화된 실패 문맥으로 남긴다.

## 15. 테스트 전략

### 15.1 자동 테스트

최소 다음 회귀를 고정한다.

- 등록되지 않은 맵과 없는 스폰이 현재 맵, 플레이어, 모드를 보존한다.
- 방 ↔ 홀 왕복 후 플레이어와 `PlayerVisual`이 새 맵의 올바른 부모에 있다.
- 맵 교체 뒤 상호작용 안내와 대화·문 어댑터가 한 번씩만 실행된다.
- `WorldState`가 `map_id/object_id`별로 깊은 복사 왕복을 한다.
- 중복 오브젝트 ID와 직렬화 불가능한 값을 거부한다.
- 허용하지 않은 슬롯 ID와 빈 슬롯 불러오기를 거부한다.
- 손상 JSON, 체크섬 불일치, 지원하지 않는 버전을 거부한다.
- 파일 시스템 각 단계 실패가 기존 현재 슬롯 또는 정상 백업을 보존한다.
- 현재 저장이 손상되고 백업이 정상일 때 자동 복구하고 복구 신호를 한 번 보낸다.
- 중요한 선택의 효과가 성공하고 다음 `line`/`choice`가 게시된 뒤에만 자동 저장한다.
- 선택 뒤 종료되는 대화는 체크포인트 없이 완료 상태를 저장한다.
- 자동 저장 요청이 겹쳐도 쓰기를 중복 실행하지 않고 최신 안정 지점을 남긴다.
- 새 게임의 첫 맵 배치가 성공하면 초기 자동 저장을 만들고, 실패하면 타이틀을 유지한다.
- 대화, 컷신, 전환 중 수동 저장을 거부한다.
- 탐색에서 연 메뉴만 수동 저장을 허용한다.
- 타이틀 로드 실패가 빈 `WorldHost`와 타이틀을 유지한다.
- 인게임 로드 실패가 현재 맵과 전체 상태를 유지한다.
- 대화 체크포인트 로드는 이벤트를 다시 선택하지 않고 저장된 안정 경계에서 재개한다.
- 여섯 슬롯 행의 순서, 읽기 전용 자동 저장, 빈 슬롯 비활성화, 키보드 포커스를 검증한다.

### 15.2 수동 수직 슬라이스

다음 순서를 실제 키보드와 화면으로 확인한다.

1. 타이틀에서 `새 게임`을 선택한다.
2. 이동, 달리기, 충돌, 방향 애니메이션을 확인한다.
3. 거울을 조사한다.
4. 화자 이름, 초상화, 표정, 대사를 확인한다.
5. 중요한 선택을 하고 다음 대사에 도착한다.
6. 자동 저장 행에 장소, 플레이 시간, 저장 시각이 표시되는지 확인한다.
7. 문으로 홀에 이동하고 스폰, 페이드, 상호작용 재결합을 확인한다.
8. `Esc` 메뉴에서 슬롯 1에 수동 저장한다.
9. 플레이어 위치, 플래그, 월드 오브젝트 상태를 바꾼다.
10. 슬롯 1을 불러와 맵, 위치, 방향, 내러티브, 월드 상태가 정확히 복원되는지 확인한다.
11. 자동 저장을 불러와 중요한 선택 다음 대사 또는 선택지에서 재개되는지 확인한다.
12. 현재 저장 파일을 의도적으로 손상시키고 정상 백업이 자동 복구되며 알림이 표시되는지 확인한다.
13. 네트워크 없이 게임을 다시 실행하고 기존 슬롯을 불러온다.

## 16. 완료 기준

다음 조건을 모두 만족해야 이번 수직 슬라이스를 완료로 본다.

1. 전역 서비스는 `GameSession`, `SceneDirector`, `SaveService` 세 개뿐이다.
2. 타이틀에 `새 게임`, `불러오기`, `종료`가 있고 별도 `이어하기`가 없다.
3. 불러오기와 저장 UI가 자동 저장 1행 + 수동 슬롯 5행을 같은 컴포넌트로 표시한다.
4. 방과 홀을 왕복해도 플레이어, Y-sort, 상호작용, 대화 연결이 정상이다.
5. 중요한 선택 뒤 다음 안정 대화 경계에 자동 저장된다.
6. 수동 저장과 자동 저장이 맵, 플레이어, 내러티브, 월드, 대화 상태를 정확히 복원한다.
7. 손상된 현재 저장은 정상 백업으로 자동 복구되고 사용자에게 알린다.
8. 모든 실패 경로가 현재 플레이와 마지막 정상 슬롯을 보존한다.
9. 자동 테스트 전체와 수동 수직 슬라이스 13단계가 통과한다.
10. 오프라인 부팅과 불러오기가 가능하며 Notion, 토큰, 네트워크 참조가 런타임에 없다.

## 17. 제외 범위

이번 구현에는 다음을 포함하지 않는다.

- 클라우드 저장
- 저장 파일 암호화 또는 치트 방지
- 슬롯 스크린샷
- 슬롯 이름 직접 편집
- 무제한 수동 슬롯
- 전투 중 저장
- 대화의 임의 글자 중간 위치 복원
- 콘텐츠 변경 뒤 모든 과거 체크포인트를 자동 변환하는 범용 마이그레이션
- 게임패드 완전 지원
- 실제 배포 플랫폼의 업적 또는 계정 연동

## 18. 후속 구현 계획 원칙

사용자가 이 설계를 승인한 뒤 별도의 현재 구현 계획을 작성한다. 구현 계획은 기존 구형 Plan 4를 수정하지 않고 새 파일로 남긴다.

계획은 최소 다음 작업 묶음으로 나눈다.

1. 맵 레지스트리, `SceneDirector`, 화면 전환, 동적 연결
2. `WorldState`와 영속 오브젝트
3. `SaveData`, `SaveRepository`, 백업 복구
4. `SaveService`, 대화 안정 체크포인트, 자동 저장
5. document-first `중요 선택` 메타데이터와 참조 문서
6. 타이틀·인게임·6행 슬롯 UI
7. 두 번째 맵과 전체 수직 슬라이스 검증

각 묶음은 테스트를 먼저 작성하고 정상 종료하는 RED를 확인한 뒤 최소 구현, 집중 GREEN, 전체 회귀, 의미 단위 커밋 순서로 진행한다.
