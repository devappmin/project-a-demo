# Project A 문서형 다이얼로그 저작 재설계

작성일: 2026-08-16  
상태: 승인됨

## 1. 배경

기존 설계는 Notion의 `Characters`, `Dialogue Scenes`, `Dialogue Blocks` 데이터베이스 세 개를 사용한다. 대사 한 줄이나 선택지 한 개가 `Dialogue Blocks`의 행 하나이며, Notion에서는 각 행도 페이지로 취급된다. 이 구조는 기계적인 동기화에는 유리하지만 다음 문제를 만든다.

- 대사가 늘어날수록 페이지 수가 지나치게 많아진다.
- 한 장면의 대화 흐름을 표의 여러 행으로 나누어 보아야 한다.
- 긴 대화, 여러 단계의 선택지, 분기 합류와 재분기를 회의 중에 읽고 고치기 어렵다.
- 기획자가 내부 키, 순번, JSON 필드와 데이터베이스 관계를 의식해야 한다.
- 실제 공동 집필 방식인 제목, 문단, 목록, 인용, 댓글 중심의 Notion 사용법과 맞지 않는다.

Project A의 핵심은 대화와 분기이며, 사용자와 디자이너가 같은 화면을 보며 대화를 고민하고 작성한다. 따라서 저작 경험을 우선하고, 기계용 구조는 가져오기 단계에서 생성한다.

## 2. 목표

- 장소 또는 이야기 묶음 하나를 Notion 페이지 하나에서 읽고 작성한다.
- 한 장소 안에 첫 방문, 아이템 보유, 선행 조건 충족 등 여러 이벤트를 함께 적는다.
- 대사 뒤 선택, 긴 후속 대화, 재선택, 반복, 분기 합류를 임의 깊이로 표현한다.
- 작성자는 한글 이름과 자연스러운 조건 문장을 사용한다.
- 조건과 결과는 인용 블록으로 본문에 명시한다.
- 주석, 질문, 대안 논의는 Notion 댓글로 통일한다.
- Codex 또는 Claude Code가 필요할 때만 문서를 가져와 게임 데이터로 가공한다.
- AI는 코드베이스에 등록되지 않은 변수를 임의로 만들지 않는다.
- 변환이나 검증에 실패하면 마지막 정상 게임 데이터를 보존한다.

## 3. 비목표

- Notion 변경 사항의 실시간 동기화
- 대사 작성자가 영어 ID, JSON, 데이터베이스 관계를 직접 관리하는 방식
- Notion 댓글을 게임 규칙의 정식 입력으로 사용하는 방식
- Notion에 접속해야만 실행되는 게임
- 기존 세 데이터베이스를 설계 승인과 동시에 삭제하는 작업
- AI의 추측만으로 검증 없이 게임 데이터를 교체하는 작업

## 4. 저작 정보 구조

### 4.1 페이지 단위

Notion의 상위 `대화 목록` 페이지 아래에 장소 또는 긴밀한 이야기 묶음별 하위 페이지를 둔다. 필수 데이터베이스는 사용하지 않는다.

예:

- 젤리뽀의 집
- 학교 본관
- 숲 입구
- 축제 전날

하나의 장소에서 서로 다른 상호작용이 많더라도 먼저 한 페이지 안에서 트리거별로 나눈다. 내용이 지나치게 커지고 서로 독립적인 이야기 묶음이 된 경우에만 페이지를 추가로 분리한다.

### 4.2 문서 계층

한 페이지는 다음 세 단계의 제목을 사용한다.

1. `트리거 · <이름>`: 언제 또는 무엇과 상호작용했는지 묶는다.
2. `이벤트 · <이름>`: 같은 트리거에서 조건에 따라 선택될 후보를 정의한다.
3. `흐름 · <이름>`: 이벤트 안의 대사와 선택지 그래프를 정의한다.

권장 예시는 다음과 같다.

```text
페이지 제목: 젤리뽀의 집

제목 1 · 트리거 · 장소 입장

제목 2 · 이벤트 · 열쇠를 가진 재방문
> 발생
> - 젤리뽀의 집에 들어왔을 때
>
> 조건
> - 교환일기 열쇠를 가지고 있음
> - 아직 열쇠를 보여주지 않음
>
> 결과
> - 열쇠를 보여줌 상태로 기록

제목 3 · 흐름 · 시작
젤리뽀 [당황]: 그 열쇠는 어디서 났어뽀…?
레티 [경계]: 왜? 이게 뭔지 알아?

선택지
- 학교에서 찾았다고 말한다 → 고백
- 주머니에 숨긴다 → 숨김

제목 3 · 흐름 · 고백
...

제목 3 · 흐름 · 숨김
...
```

`장소 입장`, `젤리뽀와 대화`, `책장 조사`처럼 같은 페이지에 여러 트리거를 둘 수 있다.

### 4.3 이벤트 선택

한 트리거 안의 이벤트는 문서에 적힌 위쪽부터 조건을 검사한다. 처음으로 모든 조건이 일치한 이벤트 하나만 실행한다.

- 구체적이고 제한적인 이벤트를 위에 둔다.
- 조건이 없는 `그 외` 이벤트는 필요한 경우 맨 아래에 둔다.
- 일치하는 이벤트가 없고 `그 외`도 없으면 대화를 시작하지 않는다.
- `그 외`가 없는 것은 유효하지만 가져오기 보고서에 경고로 표시한다.

이 규칙으로 작성자가 별도 우선순위 숫자를 관리하지 않아도 된다.

### 4.4 흐름과 선택지

모든 이벤트는 `흐름 · 시작`에서 시작한다. 선택지는 한글 흐름 이름을 목적지로 사용한다.

```text
선택지
- 기억의 조각까지 봤다고 말한다 → 전부 말함
- 열쇠 이야기만 하고 멈춘다 → 일부만 말함
```

흐름은 다음 동작을 모두 지원한다.

- 여러 문단의 대사 뒤 선택지 표시
- 선택 이후 여러 문단 진행
- 같은 분기 안에서 다시 선택지 표시
- 앞에서 정의한 흐름으로 돌아가기
- 여러 분기가 하나의 흐름으로 합류하기
- 다른 이벤트로 명시적으로 이어가기
- 이벤트 종료 후 플레이어 조작으로 복귀하기

중첩 들여쓰기로 분기를 표현하지 않는다. 이름 붙은 흐름을 평평하게 나열하고 화살표로 연결하므로 분기 깊이가 커져도 문서 구조는 일정하다.

흐름 이름은 같은 이벤트 안에서 고유해야 한다. 작성자는 `고백`, `숨김`, `대화 정리`처럼 한글만 쓴다. `confess` 같은 영어 ID는 병기하지 않는다.

### 4.5 조건과 결과

조건, 발생 시점, 결과는 일반 대사와 섞지 않고 Notion 인용 블록에 적는다. 이 정보는 개발자 전용 메타데이터가 아니라 두 작성자가 함께 읽는 정식 기획 내용이다.

인용 블록은 가장 가까운 구조 단위에 속한다.

- 이벤트 아래: 이벤트 진입 조건과 모든 정상 종료 경로에 공통인 결과
- 흐름 아래: 해당 흐름에 들어와 정상적으로 빠져나갈 때 적용할 결과
- 이름을 명시한 선택지 아래: 그 선택지를 보일 조건과 선택 직후 적용할 결과

결과 적용 시점은 다음과 같다.

- 이벤트 결과: 이벤트가 정상 종료하거나 다른 이벤트로 전환되기 직전
- 흐름 결과: 해당 흐름이 다음 흐름으로 이동하거나 종료되기 직전
- 선택지 결과: 플레이어가 선택한 직후, 목적 흐름으로 이동하기 전
- 플레이어가 대화를 취소하거나 런타임 오류로 중단된 경우: 아직 확정되지 않은 결과를 적용하지 않음

같은 조건이나 결과가 어느 단위에 속하는지 불명확하면 AI는 위치를 추측하지 않고 확인을 요청한다.

### 4.6 댓글

별도의 `주석` 본문 블록을 만들지 않는다. 연출 메모, 집필 의도, 질문, 대안과 검토 대화는 관련 문장이나 블록에 Notion 댓글로 남긴다.

- Codex 또는 Claude Code는 접근 가능한 댓글을 집필 맥락으로 참고할 수 있다.
- 댓글은 해결되거나 삭제될 수 있으므로 컴파일의 정식 입력이 아니다.
- 댓글만으로 조건, 결과, 변수 또는 분기를 생성하지 않는다.
- 댓글에서 게임 규칙이 확정되면 작성자가 그 내용을 본문의 인용 블록이나 대사·선택지에 반영한다.
- 댓글을 가져올 수 없는 환경에서도 같은 본문은 같은 게임 데이터를 만들어야 한다.

## 5. 서사 용어 사전

### 5.1 목적

Notion에서는 사람이 읽기 좋은 한글을 쓰지만 런타임에는 안정적인 키와 값 형식이 필요하다. 코드베이스에 서사 용어 사전을 두어 둘을 연결한다.

사전은 다음 범주를 다룬다.

- 캐릭터와 표정
- 참/거짓 사건 상태
- 신뢰도 같은 수치
- 인벤토리 아이템과 수량
- 퀘스트와 허용 단계
- 수집품
- 장소와 상호작용 트리거
- 실행 가능한 결과와 명령

현재 `NarrativeState`의 `flags`, `stats`, `inventory`, `quests`, `collectibles`와 기존 캐릭터 레지스트리를 기반으로 확장한다.

### 5.2 사전 항목

각 항목은 최소 다음 정보를 가진다.

- 안정적인 내부 키
- 한국어 정식 이름
- 종류와 허용 값
- 기본값
- 작성자가 이해할 설명
- 필요한 경우 허용되는 한국어 동의 표현

예:

| 한국어 정식 이름 | 내부 키 | 종류 | 설명 |
|---|---|---|---|
| 교환일기 열쇠 | `exchange_diary_key` | 아이템 | 젤리뽀 관련 교환일기를 여는 열쇠 |
| 열쇠를 보여줌 | `showed_diary_key` | 플래그 | 젤리뽀에게 열쇠 존재를 공개했는지 |
| 젤리뽀의 신뢰 | `jellyppo_trust` | 수치 | 젤리뽀와 레티 사이의 신뢰도 |
| 진실 조사 | `truth_investigation` | 퀘스트 | 진실을 조사하는 이야기 진행 단계 |

기계가 검증하는 사전을 단일 원본으로 삼고, 사람이 읽는 한국어 참고 문서는 그 원본에서 생성하거나 일치 여부를 자동 검사한다.

### 5.3 AI 매핑 규칙

AI가 조건과 결과를 처리할 때 각 표현은 다음 셋 중 하나가 된다.

1. `정확히 연결됨`: 정식 이름이나 승인된 동의 표현과 일치하여 자동 변환
2. `연결 제안`: 유력한 기존 항목이 있지만 확정이 필요하여 가져오기 미리보기에 제안
3. `확인 필요`: 대응 항목이 없거나 여러 의미가 가능하여 변환 중단

AI는 세 번째 경우 새 키를 자동 생성하지 않는다. 새 개념은 먼저 서사 용어 사전에 명시적으로 추가하고 승인한 뒤 사용한다.

## 6. 수동 가져오기 아키텍처

### 6.1 전체 흐름

```text
Notion 장소 페이지
  → Codex/Claude가 본문과 접근 가능한 댓글을 읽음
  → 서사 용어 사전과 대조
  → 정규화된 중간 자료와 진단 보고서 생성
  → 사용자 확인
  → 결정론적 검증 및 대화 그래프 컴파일
  → 원자적으로 로컬 게임 데이터 교체
  → Godot 런타임은 로컬 데이터만 사용
```

가져오기는 사용자가 요청할 때만 수행한다. 프로젝트 자체가 AI 서비스나 Notion에 상시 연결되지 않는다.

### 6.2 책임 분리

구성 요소를 다음처럼 분리한다.

- **문서 수집 단계**: 사용자가 지정한 Notion 페이지의 블록 구조와 접근 가능한 댓글을 제공한다. Notion 커넥터, MCP 또는 수동 내보내기 중 무엇을 사용하든 이후 단계의 계약은 같다.
- **AI 정규화 단계**: 제목, 인용 블록, 대사, 선택지와 자연어 조건을 중간 자료로 바꾼다. 불확실성을 진단으로 남긴다.
- **서사 사전 검증기**: 모든 캐릭터, 표정, 트리거, 조건과 결과가 등록되어 있고 값 형식이 맞는지 결정론적으로 검사한다.
- **그래프 컴파일러**: 승인된 중간 자료를 기존 `DialogueGraph` 형식으로 변환한다.
- **그래프 검증기**: 목적지, 순환, 자동 경로 한도와 런타임 계약을 검사한다.
- **원자적 작성기**: 전체 묶음 검증이 끝난 경우에만 마지막 정상 스냅샷을 교체한다.

AI 출력은 곧바로 런타임 파일이 되지 않는다. 결정론적 검증기를 반드시 통과한다.

### 6.3 중간 자료와 변경 이력

AI가 만든 정규화 자료와 소스 대응 정보는 코드베이스에 추적 가능한 파일로 저장한다. 작성자가 직접 편집할 필요는 없지만 Git diff로 다음 내용을 검토할 수 있어야 한다.

- 어떤 이벤트와 흐름이 추가·변경·삭제되었는지
- 자연어 조건이 어떤 내부 키와 연산으로 연결되었는지
- 어떤 결과가 어느 시점에 적용되는지
- Notion 원문의 어느 페이지·블록에서 왔는지

게임용 생성물과 정규화 자료는 구분한다. 런타임은 생성된 로컬 게임 데이터만 읽는다.

### 6.4 안정적인 식별자

작성자는 내부 ID를 입력하지 않는다.

- Notion 페이지와 구조 블록 식별자를 사용할 수 있으면 이를 로컬 대응표의 소스 정체성으로 사용한다.
- 내부 이벤트·흐름·노드 ID는 로컬 대응표에서 생성하고 이후 가져오기에도 보존한다.
- 한국어 제목을 바꾸었다는 이유만으로 기존 내부 ID를 즉시 교체하지 않는다.
- 원문 식별자를 사용할 수 없는 수집 방식에서는 기존 대응표와 구조를 비교해 후보를 제시하고, 이름 변경인지 새 항목인지 모호하면 사용자 확인을 요구한다.

이 대응 정보는 코드베이스에만 있으며 Notion 저작 화면에는 노출하지 않는다.

## 7. 진단과 실패 처리

### 7.1 오류

다음 문제는 가져오기와 게시를 막는다.

- 같은 이벤트 안에서 중복된 흐름 이름
- 존재하지 않는 흐름 또는 이벤트를 가리키는 목적지
- 등록되지 않은 캐릭터, 표정, 트리거 또는 서사 용어
- 값 형식이 맞지 않는 조건이나 결과
- 조건·결과의 소속 단위를 확정할 수 없음
- 종료 가능성이 없는 자동 반복
- 비어 있거나 구조를 판독할 수 없는 페이지
- AI 중간 자료와 원문 대응 정보의 불일치
- 런타임 대화 그래프 계약 위반

오류 메시지는 가능한 경우 Notion 페이지와 해당 블록, 한국어 표현, 제안 해결 방법을 함께 보여준다.

### 7.2 경고

다음 문제는 게임을 깨뜨리지 않으므로 경고로 표시한다.

- 트리거 그룹에 `그 외` 이벤트가 없음
- 어떤 선택지에서도 도달하지 않는 흐름
- 해결되지 않은 댓글이 남아 있음
- 승인된 동의 표현이 아닌 문장을 기존 용어에 연결하도록 제안함
- 지나치게 긴 대화나 선택지 문구로 UI 확인이 필요함

경고는 사용자가 검토할 수 있어야 한다. `Final`로 게시하는 자료에서 어떤 경고를 허용할지는 가져오기 미리보기에 명시한다.

### 7.3 원자성

가져오기 한 번은 선택한 문서 묶음 전체에 대해 성공하거나 실패한다.

- 오류가 하나라도 있으면 런타임 데이터를 교체하지 않는다.
- 쓰기, 검증, 백업 또는 게시 단계가 실패하면 마지막 정상 데이터로 복구한다.
- 일부 장소만 새 버전이고 나머지는 이전 버전인 혼합 상태를 만들지 않는다.
- 복구 상태를 확정할 수 없으면 자동 재시도하지 않고 복구 자료와 진단을 보존한다.

기존 원자적 스냅샷 작성기의 안전 계약을 유지한다.

## 8. 기존 Notion 데이터베이스 방식의 처리

`Characters`, `Dialogue Scenes`, `Dialogue Blocks`는 새 저작 원본으로 사용하지 않는다.

이행 순서는 다음과 같다.

1. 기존 DB와 동기화 코드는 당장 삭제하지 않고 읽기 전용 참고 상태로 둔다.
2. 현재 샘플 대화를 새 장소 페이지 템플릿으로 옮긴다.
3. 두 방식이 생성하는 런타임 대화의 의미와 실제 플레이 결과를 비교한다.
4. 새 방식의 가져오기, 검증과 플레이가 통과하면 기존 DB에 사용 중단 안내를 표시한다.
5. 기존 토큰 기반 실시간 동기화 패널은 제거하거나 명확히 비활성화하여 새 작업 흐름과 혼동되지 않게 한다.
6. 기존 DB의 최종 보관 또는 삭제는 사용자 확인을 받은 별도 작업으로 수행한다.

기존 `docs/dialogue-authoring-guide.md`는 새 장소 문서 방식에 맞게 교체한다. 이전 DB 작성법은 필요하면 마이그레이션 기록으로 분리한다.

## 9. 테스트 전략

### 9.1 문서 구조와 정규화

- 한 페이지의 여러 트리거와 여러 이벤트
- 위에서부터 첫 조건 일치 이벤트 선택
- 조건 없는 `그 외` 이벤트
- 여러 문단 뒤 선택, 선택 뒤 긴 대화, 다시 선택
- 분기 합류, 이전 흐름 복귀, 다른 이벤트 전환
- 이벤트·흐름·선택지 범위의 조건과 결과
- 댓글 유무와 관계없이 동일한 게임 규칙 생성
- 모호한 자연어와 새 용어의 차단
- 한국어 제목 변경 시 내부 ID 보존

### 9.2 결정론적 검증

- 캐릭터, 표정, 트리거와 모든 상태 키의 사전 검증
- 중복 흐름과 끊어진 목적지 거부
- 도달 불가능 흐름 경고
- 종료 없는 자동 순환 거부
- 기존 자동 실행 경로 한도 유지
- 조건 및 결과 타입과 연산자 검증

### 9.3 저장과 통합

- 정규화 실패, 그래프 검증 실패, 쓰기 실패 시 이전 바이트 보존
- 정상 게시 뒤 manifest와 실제 그래프 해시 일치
- 생성된 대화를 `DialogueGraphLoader`가 오프라인으로 로드
- `DialogueService`에서 대사, 표정, 선택지, 후속 선택지와 종료까지 재생
- 조건에 따른 이벤트 선택과 결과 적용을 실제 `NarrativeState`에서 확인
- 취소·실패 시 아직 확정되지 않은 상태 변경 복구

### 9.4 수동 확인

- 사용자와 디자이너가 템플릿을 복제해 한 장소의 대화를 작성할 수 있음
- 내부 키나 JSON을 입력하지 않고 분기 대화를 완성할 수 있음
- 가져오기 미리보기에서 변경점과 확인 필요 항목을 이해할 수 있음
- 640×360 게임 화면에서 긴 대사와 여러 선택지를 조작할 수 있음

테스트는 저장된 fixture를 기본으로 사용한다. 실제 Notion 접속은 외부 수집 경계의 선택적 확인이며 전체 테스트의 필수 조건이 아니다.

## 10. 수용 기준

다음 조건을 모두 만족하면 새 저작 방식의 1차 구현이 완료된 것으로 본다.

- 장소 페이지 템플릿 하나로 여러 트리거, 이벤트와 임의 깊이 분기를 작성할 수 있다.
- 작성자는 한국어만 사용하며 내부 ID, 순번, JSON을 관리하지 않는다.
- 조건과 결과는 인용 블록, 주석과 논의는 Notion 댓글로 구분된다.
- 댓글을 읽지 못해도 본문에서 동일한 게임 데이터를 만들 수 있다.
- 코드베이스의 서사 용어 사전 밖의 상태를 AI가 임의 생성하지 않는다.
- 변환 미리보기가 변경, 매핑, 경고와 오류를 한국어로 보여준다.
- 모든 결정론적 검증이 통과한 경우에만 로컬 게임 데이터를 원자적으로 교체한다.
- Godot 런타임은 Notion이나 인증 정보 없이 마지막 정상 대화를 재생한다.
- 기존 DB 샘플과 새 문서형 샘플의 플레이 의미가 일치한다.
- 기존 세 데이터베이스와 실시간 동기화 패널의 사용 중단 경로가 문서화된다.
