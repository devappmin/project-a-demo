# 프로젝트 인수인계와 크로스플랫폼 작업 문서 설계

- 작성일: 2026-08-16
- 대상 프로젝트: `project-a-demo`
- 참고 전용 프로젝트: `project-a` (deprecated, 수정 금지)
- 엔진: Godot 4.7
- 상태: 사용자 승인 완료
- 후속 마일스톤: 조건 분기 플레이 기반

## 1. 목적

이 설계는 새 컴퓨터나 새 에이전트 세션에서 저장소를 받은 사람이 이전 대화 기록이나 로컬 전용 보고서 없이도 현재 프로젝트를 정확히 이해하고 작업을 이어가게 한다.

완료 후에는 다음이 가능해야 한다.

1. 처음 온 사람이 `README.md`에서 실행 방법과 현재 플레이 범위를 찾는다.
2. Codex와 Claude Code가 같은 프로젝트 규칙을 읽는다.
3. Windows, macOS, Linux CI에서 같은 Python 명령으로 프로젝트를 진단하고 검증한다.
4. 구현 완료 상태와 미래 계획을 서로 다른 문서에서 확인한다.
5. 프로젝트용 Codex 스킬이 작업 종류에 맞는 원본 문서를 선택해 읽는다.
6. 다음 작업인 조건 분기 플레이 기반을 과거 설계 문서를 재해석하지 않고 시작한다.

## 2. 기본 원칙

- 저장소가 인수인계의 단일 원본이다.
- `.superpowers`처럼 Git에서 무시되는 로컬 보고서에 필수 정보를 단독으로 보관하지 않는다.
- 같은 사실을 여러 문서에 상세 복사하지 않고 한 문서만 원본으로 정한다.
- 문서는 실제 코드와 검증된 플레이 상태를 설명하며 희망 사항을 완료 상태처럼 쓰지 않는다.
- 운영체제 전용 설정, 전역 환경 변경, 절대 경로를 요구하지 않는다.
- 런타임과 기본 검증은 Notion, 토큰, 네트워크에 의존하지 않는다.
- 기존 역사 문서와 승인된 설계·계획은 삭제하거나 재작성하지 않는다.

## 3. 문서 구조와 소유권

### 3.1 `README.md`

저장소의 짧은 입구다. 다음 내용만 포함한다.

- 게임 한 문단 소개
- 현재 플레이 가능한 수직 슬라이스
- 엔진과 필수 도구
- clone 후 첫 실행 순서
- 조작법
- 표준 진단·테스트·전체 검증 명령
- 핵심 문서 링크
- 현재 마일스톤과 다음 마일스톤 링크

상세 아키텍처, 에이전트 행동 규칙, 대화 작성 규칙은 복사하지 않고 원본 문서로 연결한다.

### 3.2 `AGENTS.md`

Codex와 Claude Code가 공유하는 프로젝트 작업 규칙의 단일 원본이다.

- 작업 범위는 `project-a-demo`로 제한한다.
- deprecated `project-a`는 수정하지 않는다.
- 사용자가 요청하지 않으면 브랜치, worktree, PR을 만들지 않는다.
- 기본 작업 흐름은 현재 `main`에서 의미 단위 커밋을 남기는 방식이다.
- 작업 전후 Git 상태를 확인하고 사용자의 기존 변경을 보존한다.
- 기능과 버그 수정은 테스트 우선으로 진행한다.
- 검증은 `tools/project.py`를 표준 진입점으로 사용한다.
- 대화는 document-first, 한국어 작성, 내부 키 은닉 원칙을 유지한다.
- 런타임에 네트워크, Notion 인증, 외부 데이터베이스 의존성을 추가하지 않는다.
- 완료된 마일스톤은 같은 작업에서 상태 문서와 로드맵에 반영한다.
- 필수 인수인계 사실을 ignored 보고서에만 남기지 않는다.

개별 구현 세부사항은 `AGENTS.md`에 고정하지 않고 아키텍처 및 도메인 문서로 연결한다.

### 3.3 `CLAUDE.md`

Claude Code의 공식 import 구문을 사용해 다음 한 줄만 둔다.

```markdown
@AGENTS.md
```

실제 파일 시스템 심링크는 사용하지 않는다. Windows Git checkout 설정이나 Developer Mode에 영향을 받지 않으면서 `AGENTS.md` 하나만 수정하는 단일 원본 구조를 유지하기 위함이다.

### 3.4 `docs/PROJECT_STATUS.md`

현재 검증된 프로젝트 상태만 기록한다.

- 현재 실행 가능한 플레이 흐름
- 완성된 런타임 시스템
- 현재 콘텐츠와 맵
- 저장·대화·UI의 검증된 동작
- 수동 승인 완료 항목
- 아직 구현되지 않은 기능
- 알려진 제약과 비차단 기술 부채
- 현재 기준 검증 명령

작업 일지나 커밋별 역사는 넣지 않는다. 상태가 바뀌면 기존 문장을 갱신한다.

### 3.5 `docs/ROADMAP.md`

완료 상태가 아니라 미래 순서와 플레이어 관점의 승인 조건을 기록한다.

각 마일스톤은 다음 형식을 사용한다.

- 상태: 완료, 진행 예정, 보류
- 목표
- 플레이어가 할 수 있게 되는 행동
- 저장·불러오기 및 기존 시스템과의 호환 조건
- 자동 검증 기준
- 필요한 수동 승인
- 명시적인 제외 범위

### 3.6 `docs/ARCHITECTURE.md`

파일 나열보다 시스템 책임과 데이터 흐름을 설명한다.

```text
입력 -> 플레이어 -> 상호작용 탐색 -> 조건 이벤트 선택 -> 대화
                              |
                       Narrative/World State
                              |
                         저장·불러오기

작성 문서 -> 정규화 JSON -> 검증·컴파일 -> 런타임 대화/이벤트 데이터
```

최소 다음 경계를 설명한다.

- `AppRoot`와 UI 소유권
- `GameSession`, `SceneDirector`, `SaveService`의 책임
- 플레이어와 맵 수명 주기
- 상호작용 탐지, 라우팅, 조건 이벤트 해석, 대화 실행
- `NarrativeState`와 `WorldState`의 소유 범위
- 저장 스냅샷과 복원 트랜잭션
- document-first 작성 데이터의 런타임 게시 과정
- 테스트 계층과 표준 검증 진입점

### 3.7 기존 문서

- `docs/dialogue-authoring-guide.md`는 공동 대화 작성법의 단일 원본으로 유지한다.
- `docs/narrative-state-reference.md`는 조건, 효과, 명령, 캐릭터·표정 매핑의 참조로 유지한다.
- `docs/superpowers/specs`와 `docs/superpowers/plans`는 역사적 결정과 구현 기록으로 보존한다.
- 현재 상태나 새 작업의 출발점은 과거 계획이 아니라 `PROJECT_STATUS.md`와 `ROADMAP.md`다.

## 4. 크로스플랫폼 프로젝트 실행기

### 4.1 위치와 제약

표준 실행기는 `tools/project.py` 하나로 제공한다.

- Python 표준 라이브러리만 사용한다.
- Windows, macOS, Linux에서 같은 하위 명령을 제공한다.
- 사용자 전역 환경, 레지스트리, shell profile을 수정하지 않는다.
- 로컬 경로 설정 파일을 생성하지 않는다.
- 저장소 밖 경로에 파일을 쓰지 않는다.
- 현재 작업 디렉터리와 관계없이 저장소 루트를 스크립트 위치로부터 계산한다.

기존 `tools/run_godot.ps1`은 기존 사용자와 회귀 테스트를 위해 유지하되 새 문서의 표준 진입점으로 사용하지 않는다.

### 4.2 Godot 탐색

Godot 실행 파일은 다음 우선순위로 결정한다.

1. `--godot <path-or-command>`
2. `PROJECT_A_GODOT_BIN`
3. PATH의 `godot`
4. PATH의 `godot4`

발견한 실행 파일은 실제로 호출해 Godot 4.7 계열인지 확인한다. 찾지 못했거나 버전이 맞지 않으면 어떤 탐색을 시도했는지와 해결 예시를 표시하고 비영 종료한다.

### 4.3 하위 명령

```text
python tools/project.py doctor
python tools/project.py test [--filter <text>]
python tools/project.py editor
python tools/project.py boot
python tools/project.py check
```

- `doctor`: Python 버전, Godot 버전, 저장소 루트, 필수 파일을 확인한다.
- `test`: `tests/run_all.gd`를 실행하고 선택적 필터를 전달한다.
- `editor`: headless editor/class-cache 로드가 깨끗이 끝나는지 확인한다.
- `boot`: main scene을 짧게 headless 실행해 오프라인 부팅을 확인한다.
- `check`: doctor, 전체 test, editor, boot를 fail-fast 순서로 실행한다.

호출 방식은 shell 문법에 의존하지 않는다. CI는 설치한 Godot 명령을 `--godot`으로 전달하거나 PATH에 노출한 뒤 같은 `check`를 호출한다.

### 4.4 오류 처리

Godot가 잘못 종료 코드 0을 반환하더라도 다음 진단이 있으면 실행기는 실패로 승격한다.

- `SCRIPT ERROR`
- `Failed to load script`
- 테스트 assertion 실패 표시
- 테스트 suite 선택 또는 완료 계약의 비정상 누락

실패 시 다음 정보를 보여준다.

- 실패한 하위 명령
- 실행한 Godot 인수 목록에서 민감하지 않은 부분
- 원래 프로세스 종료 코드
- 실패를 판정한 진단 줄

토큰, 환경변수 값, 사용자 홈 경로 전체를 진단에 출력하지 않는다.

## 5. 프로젝트 Codex 스킬

### 5.1 위치

```text
.agents/skills/project-a-workflow/
├─ SKILL.md
└─ agents/openai.yaml
```

저장소 루트의 `.agents/skills`에 추적해 clone한 다른 컴퓨터에서도 Codex가 발견하게 한다.

### 5.2 역할

스킬은 프로젝트 사실을 복제하는 지식 창고가 아니라 문서 라우터이자 작업 절차다.

1. 요청을 코드, 대화 작성, 콘텐츠, 문서, 검증 중 하나로 분류한다.
2. 항상 `PROJECT_STATUS.md`와 `ROADMAP.md`를 먼저 읽는다.
3. 코드 작업이면 `ARCHITECTURE.md`, 관련 코드와 테스트를 읽는다.
4. 대화·분기 작업이면 `dialogue-authoring-guide.md`와 `narrative-state-reference.md`를 읽는다.
5. 작업 전 Git 상태와 범위를 확인한다.
6. 구현 작업에는 승인된 설계와 테스트 우선 흐름을 적용한다.
7. `tools/project.py`의 최소 관련 검증과 전체 검증을 실행한다.
8. 완료 시 상태 문서와 로드맵이 실제 결과와 일치하는지 확인한다.

스킬에는 별도 실행 스크립트나 README를 넣지 않는다. 실행 기능은 프로젝트의 `tools/project.py`, 상세 지식은 추적 문서에 남긴다.

### 5.3 발견과 검증

- `SKILL.md`의 description에는 Godot 프로젝트 작업, 대화·분기, 저장·맵·상호작용, 검증, 인수인계 요청을 명확히 포함한다.
- `agents/openai.yaml`은 간결한 표시 이름, 설명, 기본 프롬프트만 제공한다.
- skill-creator의 `quick_validate.py`로 폴더 형식을 검사한다.
- 저장소를 기준으로 새 Codex 세션에서 스킬이 목록에 나타나는지 확인한다.
- 스킬을 명시적으로 호출해 현재 상태 요약과 표준 검증 명령을 정확히 찾는지 확인한다.

## 6. README의 새 컴퓨터 흐름

README는 운영체제별 설치 상세를 길게 복제하지 않고 다음 최소 흐름을 제공한다.

1. Git과 Python 3, Godot 4.7을 준비한다.
2. 저장소를 clone한다.
3. `python tools/project.py doctor`를 실행한다.
4. Godot가 PATH에 없다면 `--godot` 또는 `PROJECT_A_GODOT_BIN`을 사용한다.
5. `python tools/project.py check`를 실행한다.
6. Godot editor에서 `project.godot`을 연다.
7. `PROJECT_STATUS.md`, `ROADMAP.md`, 필요 시 작성 가이드를 읽는다.

Python launcher 명령이 운영체제에서 `python3`인 경우 같은 스크립트를 `python3`로 실행할 수 있음을 짧게 안내한다.

## 7. 현재 상태 문서의 초기 기준

초기 `PROJECT_STATUS.md`는 다음 완료 상태를 반영한다.

- 640x360 정수 스케일 픽셀 탑다운 화면
- 이동, 달리기, 충돌, 상호작용, 방향 애니메이션
- 이름, 초상화, 표정, 연속 대사, 반복 선택지와 재합류를 지원하는 대화
- document-first 대화 작성, 검증, 원자적 로컬 게시
- 방과 홀 사이의 안전한 맵 전환
- 영속 플레이어와 월드 오브젝트
- 자동 저장 1개와 수동 슬롯 5개
- 타이틀, 불러오기, 일시정지, 저장, 확인, 알림 UI
- 중요한 선택 뒤 자동 저장과 정확한 대화 재개
- 손상된 현재 저장의 정상 백업 복구
- 오프라인 재실행과 실제 키보드 13단계 수동 승인 완료

아직 없는 기능은 명확히 분리한다.

- 범용 아이템과 인벤토리
- 아이템 획득과 사용
- NPC·장소 조건 이벤트를 위한 완전한 게임플레이 규칙
- 플레이어가 확인할 수 있는 퀘스트 진행 체계
- 실제 콘텐츠 규모의 맵과 이벤트
- 오디오, 설정, 게임패드, 배포 자동화

## 8. 로드맵 초기 기준

### 8.1 문서·인수인계 이식성

이번 작업이다. 다음 조건을 모두 만족하면 완료다.

- 문서 소유권 구조가 추적 파일로 존재한다.
- 새 컴퓨터 시작 순서가 README에 있다.
- Codex와 Claude Code가 같은 `AGENTS.md`를 읽는다.
- 프로젝트 스킬이 저장소에서 발견되고 검증된다.
- 표준 Python 명령이 Windows, macOS/Linux 호환 방식으로 설계된다.
- 필수 사실이 ignored 보고서에만 남아 있지 않다.

### 8.2 조건 분기 플레이 기반

다음 구현 마일스톤이다.

- 범용 아이템 정의와 인벤토리 상태
- 아이템 획득, 보유 조건, 사용과 소비
- 퀘스트 단계와 전이 규칙
- 장소·NPC 상호작용에서 상태에 맞는 이벤트 선택
- 대화 조건·효과와의 연결
- 저장·불러오기 전체 왕복
- 실패한 조건·효과의 상태 보존

### 8.3 젤리뽀의 집 플레이어블 시나리오

- 첫 방문
- 특정 아이템을 가진 방문
- 특정 요건을 충족한 방문

각 경우가 서로 다른 이벤트를 고르고, 이벤트 안에서 여러 문단, 선택지 뒤 추가 문단, 후속 선택지, 재합류가 가능해야 한다. 상태를 저장하고 다시 불러와도 같은 규칙이 유지되어야 한다.

### 8.4 콘텐츠 제작 확장

새 장소, 캐릭터, 조건 분기를 런타임 구조 변경 없이 문서와 데이터 추가만으로 제작하는 흐름을 검증한다.

### 8.5 데모 완성도와 배포

실제 맵 아트, 애니메이션, 오디오, 설정, 게임패드, export preset, CI/CD와 배포 검증을 다룬다.

## 9. 문서 갱신 규칙

- 구현 사실이 바뀌면 `PROJECT_STATUS.md`를 같은 변경 묶음에서 갱신한다.
- 마일스톤의 순서나 승인 조건이 바뀌면 `ROADMAP.md`를 갱신한다.
- 시스템 책임이나 데이터 흐름이 바뀌면 `ARCHITECTURE.md`를 갱신한다.
- 작업 방식이 바뀌면 `AGENTS.md`를 갱신한다.
- 대화 작성자 경험이 바뀌면 `dialogue-authoring-guide.md`를 갱신한다.
- README는 링크와 첫 실행 흐름이 바뀔 때만 갱신한다.
- 과거 specs/plans를 현재 상태에 맞추려고 소급 수정하지 않는다.

완료 메시지만으로 상태를 바꾸지 않는다. 코드, 테스트, 수동 승인 중 필요한 증거가 실제로 존재할 때만 완료로 표시한다.

## 10. 테스트와 검증

### 10.1 문서 검증

- README의 모든 저장소 상대 링크가 존재한다.
- AGENTS에서 참조하는 문서와 명령이 존재한다.
- CLAUDE의 import 대상이 존재하고 내용이 한 줄 계약을 지킨다.
- ROADMAP의 완료 상태가 PROJECT_STATUS와 모순되지 않는다.
- 문서에 현재 컴퓨터의 절대 경로나 토큰 값이 없다.
- deprecated 프로젝트를 작업 대상으로 안내하지 않는다.

### 10.2 실행기 검증

- 명시적 `--godot`을 우선한다.
- 환경변수와 PATH fallback을 순서대로 사용한다.
- 잘못된 경로와 잘못된 버전을 비영 종료한다.
- filter 인수를 테스트 러너에 정확히 전달한다.
- 실제 Godot 비영 종료를 보존한다.
- 종료 코드 0과 script-load 오류 조합을 실패로 승격한다.
- 깨끗한 테스트, 에디터, 부팅은 성공한다.
- 명령 인수가 shell 문자열 결합 없이 subprocess argument list로 전달된다.

### 10.3 스킬 검증

- 형식 validator를 통과한다.
- 새 세션에서 저장소 스킬로 발견된다.
- 상태 요약 요청이 PROJECT_STATUS를 사용한다.
- 다음 작업 요청이 ROADMAP을 사용한다.
- 대화 작성 요청이 작성 가이드와 상태 참조를 사용한다.
- 일반 코드 작업에서 불필요한 역사 문서를 전부 로드하지 않는다.

## 11. 완료 기준

1. 승인된 모든 추적 문서가 존재하고 책임이 겹치지 않는다.
2. README만 보고 새 컴퓨터에서 doctor와 check를 실행할 수 있다.
3. Codex와 Claude Code가 `AGENTS.md` 하나를 공유한다.
4. 프로젝트 스킬이 공식 저장소 위치에 있고 형식·발견·기본 동작을 검증한다.
5. Python 실행기가 외부 패키지와 운영체제 전용 설정 없이 동작한다.
6. 기존 전체 Godot 테스트, headless editor load, offline boot가 계속 통과한다.
7. 현재 완료 상태와 수동 승인 결과가 추적 문서에 보존된다.
8. 다음 마일스톤이 조건 분기 플레이 기반으로 명확히 정의된다.
9. Git 상태가 깨끗하고 의미 단위 커밋이 남는다.

## 12. 제외 범위
